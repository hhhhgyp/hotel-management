# 接口测试说明（扩展）

> 本文档是核心测试流程（01~05）之外的「扩展 / 加分项」，说明第二层测试——**接口测试**。

## 一、什么是接口测试，为什么需要它

一个软件系统的测试通常分多层，形成「测试金字塔」：

```
         ▲ 越往上越慢、越贵、数量越少
        /‾‾\
       / UI \
      / 测试 \      Playwright 开浏览器点页面（慢，模拟真实用户）
     /‾‾‾‾‾‾‾‾\
    / 接口测试  \     requests 直接发 HTTP（快，测后端逻辑）
   /‾‾‾‾‾‾‾‾‾‾‾‾\
  /   单元测试     \   测单个函数（最快，本项目未展开）
 /‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\
```

- **UI 测试**测「界面长什么样、按钮能不能点」，单条要几秒。
- **接口测试**绕过浏览器，直接向服务器发 HTTP 请求，检查**状态码、重定向、返回内容**，单条只要几十毫秒。

**为什么两层都要**：UI 测试保证「用户能正常用」，接口测试保证「后端逻辑正确」。接口测试快得多，能在早期更快、更便宜地发现问题。

## 二、本项目接口测试做了什么

用 `requests` 直接打被测应用的后端接口，覆盖登录、房型、房间、预订、退房 5 类，共 **13 条用例**（见 `tests/test_api.py`）。

| 模块 | 用例数 | 验证点 |
|------|--------|--------|
| 登录 / 鉴权 | 3 | 正确登录 302 跳转、错误密码 200 报错、未登录访问 302 跳登录页 |
| 房型 | 2 | 新增成功、价格 = 0 被拒绝 |
| 房间 | 3 | 新增成功、房号重复拒绝、楼层越界拒绝 |
| 预订 | 4 | 预订成功 + 状态流转、手机号非法、当天退房、预订已入住房间 |
| 退房 | 1 | 退房后订单变「已退房」 |

## 三、两个关键知识点

### 1. requests.Session 保持登录

```python
s = requests.Session()
s.post(f"{base_url}/login", data={"username": "admin", "password": "admin123"})
# Session 自动保存登录返回的 Cookie，后续请求自动带上，等价于「保持登录状态」
```

### 2. allow_redirects=False 看状态码

```python
r = s.post(url, data=..., allow_redirects=False)
assert r.status_code == 302                      # 成功 → 重定向
assert r.headers["Location"].endswith("/rooms")  # 跳转到哪
```

后端**成功时返回 302 重定向，失败时返回 200**（留在表单页并带错误提示）。用 `allow_redirects=False` 不让 requests 自动跟随跳转，才能「看到」302 状态码和跳转目标——这正是接口测试和 UI 测试的区别：UI 测试看最终页面，接口测试看 HTTP 层的原始响应。

## 四、和 UI 测试的对比（面试常问）

| 维度 | UI 测试（Playwright） | 接口测试（requests） |
|------|----------------------|---------------------|
| 走浏览器 | 是 | 否 |
| 单条耗时 | 秒级 | 毫秒级 |
| 测什么 | 界面、交互、渲染 | 状态码、重定向、后端逻辑 |
| 数量（金字塔） | 少 | 多 |
| 稳定性 | 易受页面结构影响 | 更稳定 |

本项目同一套业务规则，两层各测一遍：UI 测试保证「用户操作流程正确」，接口测试保证「后端契约正确」。
