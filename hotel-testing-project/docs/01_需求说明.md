# 需求说明（含测试需求）

> 文档作用：测试的第一步是「读懂需求」。本文档描述被测系统的功能需求、业务规则，以及由此推导出的测试需求。

## 一、项目背景

「酒店管理系统」是一个内部使用的后台管理系统，供前台/管理人员进行房型、房间、预订的日常管理。本系统为练手项目，采用内存数据模拟数据库。

**测试角色**：本文档从「测试工程师」视角，把需求拆解成可测试的规则。

## 二、功能模块

| 模块 | 功能点 | 说明 |
|------|--------|------|
| 登录/鉴权 | 登录、退出 | 管理员账号登录；未登录不能访问业务页面 |
| 房型管理 | 新增、列表、删除 | 维护房型的名称、价格、可住人数 |
| 房间管理 | 新增、编辑、删除、搜索、筛选 | 维护房间的房号、房型、楼层、状态 |
| 预订管理 | 新增预订、退房 | 客人预订房间；退房释放房间 |
| 搜索/筛选 | 按房号搜、按状态/房型筛 | 快速定位房间 |

## 三、业务规则（校验规则）

这些规则是**测试用例设计的依据**，每条规则都要有对应测试用例覆盖。

### 3.1 登录
- 用户名 `admin`、密码 `admin123` 为合法凭证。
- 用户名或密码错误时，提示「用户名或密码错误」，不进入系统。
- 用户名/密码为空时，同样登录失败。

### 3.2 房型
| 字段 | 规则 |
|------|------|
| 名称 | 必填 |
| 价格 | 必填；必须是数字；**必须大于 0** |
| 可住人数 | 必填；必须是数字；范围 **1~10** |

### 3.3 房间
| 字段 | 规则 |
|------|------|
| 房号 | 必填；**全局唯一** |
| 房型 | 必须是已存在的房型 |
| 楼层 | 必填；必须是数字；范围 **1~30** |

房间状态流转：`空闲` →（预订）→ `已预订` →（退房）→ `空闲`

### 3.4 预订
| 字段 | 规则 |
|------|------|
| 客人姓名 | 必填 |
| 手机号 | 必填；**11 位数字且以 1 开头** |
| 身份证号 | 必填；**18 位，前 17 位数字，末位数字或 X** |
| 入住/退房日期 | 必填；**退房日期必须晚于入住日期**（至少住一晚） |
| 房间 | 必须是有效房间；**只有「空闲」状态可预订** |

预订后房间状态自动变为「已预订」；退房后房间状态自动变回「空闲」。

## 四、测试需求（测试重点）

从上述规则，提炼出测试重点与优先级：

| 优先级 | 测试重点 | 理由 |
|--------|---------|------|
| 高 | 预订的日期范围、房间冲突校验 | 直接影响业务正确性与营收 |
| 高 | 手机号、身份证格式校验 | 数据质量，后续影响客人联系 |
| 中 | 价格、可住人数、楼层边界值 | 常见输入错误高发区 |
| 中 | 房号唯一性 | 数据一致性 |
| 中 | 登录鉴权 | 安全性 |
| 低 | 搜索/筛选展示 | 易用性 |

## 五、测试范围边界

- **在范围内**：上述所有功能的 UI 层功能与校验测试。
- **不在范围内**（本次不测）：接口/性能/安全专项测试（可作为后续扩展）。
